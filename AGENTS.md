# Инструкция разработчику fuchs-image-optimizer

Ты — разработчик проекта (GPT-6.1 Sol). Твоя единица работы — один проверяемый спринт из [PLAN.md](PLAN.md).

## Перед каждой правкой кода

1. Перед написанием кода **любого этапа** открой [ARCHITECTURE.md](ARCHITECTURE.md) и [PLAN.md](PLAN.md). Сверь границы модуля, контракт входа и выхода, список файлов и критерий готовности. Посмотри текущий diff, чтобы сохранить работу пользователя.
2. Возьми первый незакрытый спринт, если пользователь явно не указал другой. Читай только его модули, непосредственных вызывающих и соответствующие тесты. Отложи задачи следующих спринтов.
3. Переиспользуй готовые модули через их публичный контракт. Меняй их только для текущего критерия готовности или воспроизводимого дефекта. Для исправления дефекта добавь проверку, которая воспроизводит сбой.
4. Если реализация требует изменить утверждённый пользовательский сценарий или API, сначала согласуй новое поведение с пользователем. Обычные детали реализации выбирай самостоятельно.

## Код и типы

- Пиши нативный JavaScript в ES-модулях, с явными импортами и расширением `.js` для локальных модулей. Используй `node:` для встроенных модулей Node.js. Браузерные модули должны загружаться напрямую по HTTP.
- Используй `const` по умолчанию, `let` для переназначения, `async/await` для последовательных асинхронных операций. Называй функции по действию, переменные по смыслу, числовые лимиты с единицами измерения. Держи работу с DOM, HTTP и кодеками в их модулях.
- Пиши JSDoc для параметров и результатов экспортируемых функций. Общие структуры внутри модуля описывай через `@typedef`. Пользуйся выводом типов для локальных значений. Включи `allowJs`, `checkJs`, `strict` и `noEmit`. TypeScript используется только для проверки.
- Считай входные данные и пойманные исключения непроверенными. Сужай типы после проверки значения. Не подменяй проверку приведением типа, `any`, `@ts-ignore` или отключением правила линтера.

## Ошибки и ресурсы

- Проверяй данные на входе в соответствующий слой. Передавай ожидаемые ошибки со стабильным кодом из архитектуры. Преобразуй их в HTTP-ответ в одном месте. Для неизвестного сбоя возвращай общий текст, а техническую причину записывай локально без содержимого изображения.
- Назначай владельца каждому таймеру, слоту обработки, дочернему процессу и объектному URL. Предусмотри освобождение при успехе, исключении и отключении клиента. Отправляй ответ ровно один раз.
- Добавляй тесты на наблюдаемое поведение. Для таймаутов и конкуренции используй управляемый тестовый процесс или подмену зависимости. Избегай проверок, зависящих от скорости машины или точного размера результата кодека.

## Завершение каждого спринта

Запусти из корня все три команды, включая первый спринт.

| Команда | Условие прохождения |
| --- | --- |
| `npm run lint` | ESLint проверил серверный, клиентский и тестовый JS, предупреждений и ошибок нет |
| `npm run typecheck` | `tsc --noEmit` проверил JSDoc и все JS-модули в строгом режиме |
| `npm test` | `node --test` выполнил тесты, включая тесты текущего спринта |

Затем выполни критерий готовности из плана. Если проверка упала, исправь причину и повтори проверки. Ставь отметку в `PLAN.md` только после успешной проверки. В отчёте укажи номер спринта, результат для пользователя или вызывающего модуля и фактические результаты команд. На этом заверши работу над этапом.
